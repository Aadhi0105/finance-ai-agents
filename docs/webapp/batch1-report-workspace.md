# Batch 1 — local report workspace and read-only backend

Status: implemented and locally verified on 30 October 2026. This is an offline
application-development batch, not production release approval.

## What this adds

One browser workspace connects Keystone's four existing calculation engines to
saved reports and evidence. An analyst can find a report, see its period and
recorded outcome, inspect its limitations, open the original HTML, and inspect or
download registered evidence.

For example, opening **Financial close → Monthly financial close** shows the
synthetic June budget profit of **EUR 60.00**, actual profit of **EUR 65.00** and
**EUR +5.00** variance. The process completed, but its financial-review status is
still **Review required**. The saved HTML and close JSON explain the supplied
budget, actuals, calculation and lineage. Nothing refreshes when a page opens.

The earlier `keystone-showcase/` is a separate design prototype. This workspace
uses outputs generated by the existing engines rather than hard-coded report
mockups. All examples are still synthetic; company names in fixtures do not turn
those figures into verified company facts.

The preparer writes **five reports and twenty registered artifacts**. Agent 3's
held publication outcomes and Agent 1's review draft remain visible. Stub news
scores are not accepted sentiment; no forward-return prediction is introduced.

## Start the workspace

Use the repository's Python virtual environment. Install **Node.js 24** and
**pnpm 11.25.0** through your normal development setup. No API keys are needed.
Run these commands from the repository root:

```bash
.venv/bin/python -m pip install -r requirements-web.txt
cd web
pnpm install --frozen-lockfile
pnpm run build
cd ..
.venv/bin/python -m keystone.workspace prepare --destination output/workspace-demo
.venv/bin/python -m keystone.workspace serve --workspace output/workspace-demo --port 8765
```

Open [the local workspace](http://127.0.0.1:8765/) in a browser. Keep the terminal
running, and press Ctrl+C there to stop the server. If another program uses that
port, pass a different port between 1024 and 65535 and open the matching address.

Preparation runs each engine locally from fixtures, forces local statistics and
fixture providers, and restores the caller's environment settings afterwards.
It makes no provider or model requests. Installation itself requires network
access unless dependencies are already cached.

### Reopening and preparing a fresh copy

To reopen an existing workspace, run only `serve` with its directory. Preparation
refuses to overwrite an existing destination. For a fresh example, choose a new
directory, such as `output/workspace-demo-2`, and use that same path for `serve`.

If preparation fails, its partial directory is not an accepted workspace. Keep
it for diagnosis and use a new destination for the next attempt. The catalogue
is written only after all engine exports complete, and is then validated.

Local development preview for this batch was prepared at
`output/workspace-batch1-fixed/`; it is ignored by Git. From an existing checkout
where that directory is present, reopen it with:

```bash
.venv/bin/python -m keystone.workspace serve --workspace output/workspace-batch1-fixed --port 8775
```

### Frontend development

After preparation, run the backend on port 8765 in one terminal. In another:

```bash
cd web
pnpm dev
```

Vite binds to loopback and proxies `/api` to `http://127.0.0.1:8765`. For the
single-server preview, rebuild with `pnpm run build` and use the FastAPI address.
Reload the browser after a rebuild. Node is needed to build or develop the UI;
the built UI is served by Python without a Node process.

## Application structure

```text
Operator-only preparation
    → existing agent engines + synthetic fixtures
    → private original run/state files
    → copied, explicitly registered HTML / JSON / PNG files
    → catalogue with sizes, SHA-256 hashes and generation identity

React browser workspace
    → FastAPI GET / HEAD requests on 127.0.0.1
    → validated catalogue and registered saved files
```

| Location | Responsibility |
| --- | --- |
| `keystone/workspace/prepare.py` | Generate fresh isolated offline examples using existing engines |
| `keystone/workspace/catalog.py` | Validate the bounded inventory, file names, sizes and content hashes |
| `keystone/workspace/api.py` | Serve metadata and registered evidence through read-only routes |
| `keystone/workspace/__main__.py` | Separate operator commands for preparation and local serving |
| `web/src/` | React/TypeScript navigation, lists, report details, evidence inspection and responsive styling |
| `tests/test_workspace.py` | Offline integration, non-mutation and file-access boundary checks |

### Saved directory layout

```text
output/workspace-demo/
  catalog.json                  # explicit synthetic run and artifact inventory
  runs/
    research-example/           # registered reports, evidence, charts and inputs
    monitoring-example/
    events-example/
    news-example/
    close-example/
  _private/                     # original preparation state; never exposed by API
```

No existing `output/` tree is scanned or automatically imported. The operator
selects exactly one workspace at server startup. The frontend cannot select a
filesystem path or a different database. The catalogue records the preparation
time, base Git commit, dirty-worktree flag, preparer-file hash and original agent
run identifiers. A dirty flag means the commit alone does not identify all code
used for that example; it is not a signed release attestation.

### Read interface

| Route | Purpose |
| --- | --- |
| `GET /api/workspace` | Synthetic classification, generation identity, capability flags and runs |
| `GET /api/runs` | Saved runs; optional `?agent=agent1` through `agent4` filter |
| `GET /api/runs/{id}` | One registered run and its artifact links |
| `GET /api/runs/{id}/files/{name}` | Exact registered HTML, JSON or PNG file |
| `GET /` and `/assets/{name}` | Built UI and its JavaScript/CSS assets |

HEAD is supported. Mutation methods are refused. There is no HTTP preparation,
execution, upload, approval, correction or arbitrary-file endpoint.

## Review and access boundaries

- Execution status and financial review are distinct fields. A completed engine
  process does not approve its output. Every prepared example requires review.
- File lengths and SHA-256 hashes are checked on each metadata/artifact request.
  Missing, changed, invalid or symlinked evidence makes the catalogue unavailable
  with a generic 503 response. A displayed summary is a saved browser snapshot;
  reload to recheck it. “Matched on load” is not continuous monitoring.
- A hash match establishes consistency with this local catalogue. It does not
  authenticate an issuer, establish data rights or prevent a local operator from
  replacing both the catalogue and its files.
- Only registered files are delivered. Path traversal, unregistered names and
  symlinks inside the served file tree are refused. Inventory/file-size bounds
  keep this first implementation deliberately small.
- Original HTML is sandboxed without scripts, forms or external resources. Both
  the iframe and report response explicitly allow downloads so original report
  links work in the workspace and when opened separately. Agent 4 keeps its
  original `close-june.html` / `close-june.json` filenames so evidence and history
  links resolve within the registered inventory. HTML can display registered
  local charts and inline images. JSON downloads retain
  their saved bytes; the inspect panel truncates very long previews at 100,000
  characters and offers the complete download.
- The supported server command binds only to `127.0.0.1`, checks local Host and
  same-origin requests, and sends no-store responses. These controls do not
  authenticate a user or isolate this Mac from other local processes/users.
- Outputs and private preparation state remain local, gitignored files. This is
  neither an encrypted store nor an independent backup. Existing `.env` files,
  arbitrary reports and databases are not exposed as web assets.

Keep this server local. Team or enterprise access requires a separate application
design and acceptance: authentication, permissions, durable job execution,
approval integrity, audit retention and deployment hardening.

The [native report refinement](native-reports/README.md) specifies direct report
sections and interactive charts. [Part 2A](native-reports/part2a-data-layer.md)
implements registered native JSON and a read-only endpoint for all five synthetic
workflows. [Part 2B.1](native-reports/part2b1-reader.md) adds a native Agent 1
summary/key-figure reader. [Part 2B.2](native-reports/part2b2-research.md) adds Agent 1
supporting analysis and exact numerical tables. [Part 2C](native-reports/part2c-charts.md)
adds interactive Agent 1 graphs with point/source inspection and keyboard controls.
[Part 3A](native-reports/part3a-events.md) adds Agent 3's native past-event report
with sample metadata, interactive diagnostic bars and readable review requirements.
[Part 3B](native-reports/part3b-news.md) adds native news cards, saved coverage and
separate diagnostic text-tone graphs. Agents 2/4 retain their existing saved-HTML
reader. Verified event-relative path projection and authorised live-source
integration remain later work.

This batch supplies the viewing layer and a narrow read API. Running agents from
the browser, persistent multi-user application state, uploads, authenticated
approvals, provider integration and hosting remain future work. The existing
CLI operation layer remains the place for authorised controlled execution.

No production acceptance gate advances merely because the reports are visible
in a web interface. Yahoo access rights remain unresolved; no live Yahoo data
was fetched for this batch. Independent backup is deferred at the user's request
until suitable storage is available. User interpretation review, clean-machine
recovery and authorised real-company Agent 4 acceptance remain separate work.
